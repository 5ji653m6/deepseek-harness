# Agent Note: Per-user web GUI

Status: implemented

English | [中文](2026-09-15-per-user-web-gui.zh.md)

## Problem

The web GUI was single-tenant: the browser cookie carried no identity, every token holder saw and resumed every Session, and MCP servers received process-environment credentials at mount time. The deployed HRMS sidecar (verify presented credentials against Frappe, execute as that user, audit) could not reach the browser because `BrowserAuth` gates everything under `/api` and `/`, so no composition-only change can identify the browser caller.

## Decision

The authenticated browser subject becomes the single caller identity, sourced from Frappe token login. `POST /api/hrms/login` accepts an HRMS email plus an `api_key:api_secret` pair, verifies it with `GET {hrmsBaseUrl}/api/method/frappe.auth.get_logged_user` and `Authorization: token <pair>` before issuing identity, requires the returned user to equal the presented email case-insensitively, and answers every failure class with the same plain 401. On success the route stores the pair in a process-lifetime server-side vault bound to the subject and mints a subject-carrying signed cookie; the pair never enters the cookie, a response body, or a log. `POST /api/hrms/logout` drops the held pair and clears the cookie. The login and logout routes mount only when the owning plugin's `hrmsBaseUrl` config is present and valid; absent config keeps the GUI single-operator, and a malformed URL fails plugin load.

The cookie payload gains an optional `subject`; subject-less cookies from the process-token exchange decode unchanged, so the deployed secret and every existing session keep working. `SessionHeader` gains an optional `owner` stamped at creation from the verified dispatch subject and decoded leniently. The field is the sole structural addition of Session format V4, which ships through the adjacent [V3-to-V4 migration](../../../../packages/session/session-format-v3-to-v4/README.md); committed v3 generations are never rewritten, and restored v3 records carry no owner ([format decision](../architecture/2026-08-31-released-session-format-migrations.md)). The session corpus listing and search filter rows by header owner: a subject sees only Sessions it owns and the ownerless process-token path sees only ownerless Sessions. Resume, adoption, history page/follow, fork, and log export check the same ownership and answer mismatches with the same not-found silence a missing Session produces, never a 403 that would reveal another subject's Session exists. Internal Host work — no active browser dispatch on the async chain — keeps full access, so background drivers (goals, schedules, subagent routing) are unaffected.

Caller attribution crosses package boundaries through two process-global `Symbol.for` slots: Connection's `apply` publishes a reader of its `AsyncLocalStorage` dispatch marker on `dsh.session-controller.callerSubjectReader`, and the matching runner `runWithCallerSubject` on `dsh.session-controller.callerSubjectRunner`, both in cordis effects; the /api route and Gateway WebSocket upgrade run each dispatch inside the marker. Session filtering reads the reader without value-importing `dsh-client-connection` (which the package-dependency policy reserves for Connection's own Host entry), and session-controller uses the runner to admit each prompt under its Session owner's subject, so the agent-loop driver chain — which starts inside the admission — presents the owner's headers on every tool call. The marker wraps the subject in an object so consumers distinguish "no browser dispatch" (internal work) from a subject-less browser dispatch.

The streamable-http MCP transport gains an optional `resolveRequestHeaders?: (subject: string | undefined) => Record<string, string>` consulted per request through a custom fetch, with the caller subject active at request time. When `dsh-client-connection` provides the HRMS header source, `mcp-client` wires the resolver to it: `X-HRMS-User` carries the owning Session's subject and `X-HRMS-User-Token` its server-held pair, matching the deployed Track 1 header contract. Per-request resolution is what makes one shared app-level connection safe for concurrent owners: headers frozen at establishment would serve every later call with the establishing subject's credentials, and establishment inside one owner's dispatch would bleed those credentials into every other owner's calls. Absent resolver or subject resolves no headers, keeping single-operator behavior byte-identical and letting the per-user sidecar keep rejecting empty headers until the operator opts in.

## Alternatives considered

**Add a peer-required value import of `dsh-client-connection` for session-controller.** The dependency policy rejected the unclassified value import; classifying it would let any Host package reach Connection's internals. The process-global slot keeps the reader contract to one function while the policy lists stay untouched.

**Enforce ownership in the MCP transport via per-user connection pooling.** One shared connection with per-request header resolution matches the deployed Track 1 verify-don't-trust contract; per-user pooling multiplies server processes and tool registrations for no security gain, since the sidecar verifies every presented credential. The rejected middle ground was per-establishment resolution: headers frozen at establishment inside one owner's dispatch would serve every other owner's calls with the first owner's credentials.

**Stamp identity from a parallel identity store or client-supplied headers.** The Session owner and the server-held token vault are the only identity sources; browser-supplied `X-HRMS-*` values on ordinary API calls are never trusted, and the transport reads the subject from the dispatch marker, not from request headers.

**Answer ownership mismatches with 403.** Not-found silence prevents probing which Session ids exist under another subject; the corpus filter and every checked surface agree on the same silence.

## Consequences

Owned Sessions are invisible to other subjects and to the ownerless path, but realtime `api-session/added` event pushes are not per-subject filtered — a foreign Session row can appear transiently until the next list refresh re-filters. MCP headers reflect the subject active when each request is issued, so a request outside any owner dispatch (startup, timer-driven reconnect work) presents no HRMS headers until an owned turn runs; a restart clears the token vault, and still-valid cookies simply present no HRMS headers until the next login. Per-user enforcement stays the operator's `HRMS_PER_USER=1` sidecar choice: this change never hard-cuts over, and subject-less cookies behave exactly as before.
